## 1. Задача и зачем это нужно

**Цель:** по данным заказа (оплата, доставка, задержка и т.д.) заранее оценить, останется ли покупатель **недоволен** покупкой.

**Как определяем недовольство:** если оценка в отзыве `review_score` равна **1 или 2** — ставим `target = 1`, иначе `target = 0`.

**Задача:** бинарная классификация (два класса: доволен / недоволен).

---

## 2. Какие метрики используем и почему

| Метрика | Что означает простыми словами | Как используем |
|---------|------------------------------|----------------|
| **F1-score** | Насколько хорошо модель находит **недовольных** и не путает их с довольными (баланс точности и полноты) | **Главная.** По ней выбираем финальную модель |
| **Precision (точность)** | Из всех, кого модель назвала «недоволен», сколько действительно недовольны | Смотрим дополнительно |
| **Recall (полнота)** | Из всех реально недовольных, скольких модель нашла | Смотрим дополнительно |
| **ROC-AUC** | Насколько хорошо модель **упорядочивает** заказы от «более рискованных» к «менее рискованным» | Дополнительная, **не единственная** для выбора модели |

### Почему не accuracy (доля правильных ответов)

В данных только **~13%** заказов с плохим отзывом. Модель может почти всегда говорить «всё хорошо» и получить accuracy около 87%, но **не найдёт ни одного недовольного клиента**. Поэтому accuracy для нас обманчива.

### Почему F1 важнее ROC-AUC в нашей постановке

- **F1** отвечает на вопрос: «Мы реально находим недовольных?»
- **ROC-AUC** отвечает на вопрос: «Мы умеем различать рискованные и безопасные заказы по вероятности?»

Обе метрики полезны, но если у модели **выше ROC-AUC, а F1 ниже** — для нас это хуже: модель «осторожная», редко ставит метку «недоволен», и мы пропускаем проблемные заказы.

**Правило выбора:** при споре метрик побеждает **больший F1 на проверочной выборке (validation)**.

- **Почему выбрали:** реальные заказы бразильского маркетплейса, есть отзывы, оплата, доставка — всё нужно для нашей задачи.

  - для обучения модели: **96 358 строк, 9 столбцов** (8 признаков + `target`, `data/processed/df_model.csv`).
- **Дисбаланс:** доля недовольных (`target = 1`) — **12.8%**. Класс редкий, поэтому используем F1 и `class_weight='balanced'` в моделях.

## 4. Подготовка данных

### Очистка

| Что делали | Как |
|------------|-----|
| Пропуски | Удалили строки без нужных полей |
| Дубликаты | Убрали повторяющиеся строки в заказах и отзывах |
| Типы данных | Даты перевели в формат datetime |
| Выбросы | Метод **IQR**: слишком большие/маленькие значения **обрезали** (не удаляли строки). Например, по сумме оплаты обрезано ~7.5 тыс. значений — см. `dataset_meta.json` |

### Новые признаки (feature engineering)

| Признак | Смысл |
|---------|--------|
| `payment_value` | Сколько заплатили за заказ |
| `price` | Суммарная цена товаров |
| `freight_value` | Стоимость доставки |
| `items_count` | Сколько позиций в заказе |
| `payment_installments` | Сколько платежей (рассрочка) |
| `delivery_time_days` | Сколько дней шла доставка |
| `delivery_delay_days` | На сколько дней опоздали относительно обещанной даты |
| `review_text_length` | Длина текста отзыва |

**Анализ до обучения:** посмотрели корреляцию признаков с `target` (ноутбук `1_eda.ipynb`). Сильнее всего связаны срок и задержка доставки; связь в целом слабая — поэтому пробовали нелинейные модели (деревья, бустинг).

### Что показывают графики (кратко)

1. **Распределение оценок** — большинство отзывов хорошие (4–5), плохих мало → нужна метрика для редкого класса (F1).
2. **Срок доставки** — у части заказов очень долгая доставка; экстремумы обрезали при очистке.
3. **Задержка vs оценка** — при плохих оценках задержка в среднем больше.
4. **Тепловая карта корреляций** — признаки не дублируют друг друга сильно.

## 5. Разбиение на выборки и утечка данных (data leakage)

**Как делим:**
- сортируем заказы по дате покупки;
- **64%** — обучение (самые старые),
- **16%** — проверка при обучении (validation),
- **20%** — тест (самые новые заказы).

**Почему так честно:** модель учится только на прошлом и проверяется на будущем — как в реальной жизни.

**Утечки нет, потому что:**
- в признаки **не** входит сама оценка `review_score` (из неё только сделали `target` для обучения);
- суммы и сроки считаются **только по одному заказу**;
- в обучение не попадают заказы, которые по времени идут **после** тестовых.

**Замечание:** длина текста отзыва (`review_text_length`) известна только когда отзыв уже есть. В учебной задаче это допустимо; в продакшене такой признак появится только после отзыва.

## 8. Финальная модель и обоснование выбора

**Выбрали: Random Forest** (`models/best_model.pkl`).

### Почему именно он

1. **Лучший F1 на проверочной выборке** — а это наша главная метрика.
2. **Gradient Boosting** имеет **самый высокий ROC-AUC (0.834)**, но **F1 на тесте всего 0.356** — модель плохо помечает недовольных при обычном пороге 0.5.
3. **LightGBM** почти догоняет Random Forest по F1 на тесте (0.476 vs 0.475), но на **validation** Random Forest был стабильнее лучше — по нашим правилам выбираем по validation F1.
4. **XGBoost** близок по качеству, но чуть ниже F1 на validation.
5. После **подбора гиперпараметров** Random Forest **остался лидером по F1**.

### Одной фразой

> ROC-AUC показывает, умеет ли модель **ранжировать** риск. F1 показывает, находит ли она **недовольных**. Нам важнее второе — поэтому Random Forest, а не модель с максимальным ROC-AUC.
