## 1. Введение и постановка задачи

**Бизнес-вопрос:** можно ли по данным заказа (оплата, доставка, задержка) заранее понять, что клиент останется недоволен?

**Формулировка:** бинарная классификация. Если `review_score` ∈ {1, 2} → класс «недоволен» (`target = 1`), иначе «доволен» (`target = 0`).

**Данные:** [Brazilian E-Commerce (Olist)](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce), ~99 тыс. заказов после объединения таблиц.

**Главная метрика — F1 для класса «недоволен».** В выборке только ~13% плохих отзывов: модель, которая всегда говорит «всё хорошо», даст accuracy ~87%, но не найдёт проблемных клиентов. F1 балансирует точность и полноту по редкому классу.

**Дополнительно:** precision, recall, ROC-AUC. ROC-AUC показывает качество ранжирования по вероятности; **финальную модель выбираем по F1 на validation**, потому что нам важнее находить недовольных, а не только правильно упорядочивать риск.

## 3. Обработка и подготовка данных

**Очистка:** удаление строк с пропусками в ключевых полях, дедупликация, приведение дат к `datetime`.

**Выбросы:** метод IQR — экстремальные значения **обрезаются** (строки не выкидываем). Пример: по `payment_value` обрезано ~7.5 тыс. значений (см. `dataset_meta.json`).

**Признаки (на один заказ):**

| Признак | Смысл |
|---------|--------|
| `payment_value`, `price`, `freight_value` | Деньги |
| `items_count`, `payment_installments` | Состав и оплата |
| `delivery_time_days`, `delivery_delay_days` | Срок и опоздание |
| `review_text_length` | Длина текста отзыва |

**Разбиение по времени** (сортировка по `order_purchase_timestamp`): train 64% → validation 16% → test 20%. Так модель не «видит будущее» при обучении.

**Утечки нет:** в признаки не входит `review_score`; агрегаты считаются только внутри заказа.

*Замечание:* `review_text_length` в проде доступен только после отзыва; в учебной постановке оставили как прокси.

## 4. Baseline-модель

**Модель:** логистическая регрессия (`class_weight='balanced'`), признаки стандартизированы.

**Зачем:** простая линейная нижняя граница; все сложные модели сравниваем с ней.

| Метрика (test) | Значение |
|----------------|----------|
| F1 | 0.443 |
| ROC-AUC | 0.811 |

Код: `notebooks/2_baseline.ipynb`, `src/modeling.py`.

## 5. Эксперименты

Формат: **гипотеза → проверка → результат**.

### Эксп. 1 — Нелинейные модели лучше baseline

| | |
|---|---|
| **Гипотеза** | Деревья/бустинг поймают нелинейную связь доставки с недовольством |
| **Проверка** | 6 моделей с одинаковым split, метрики на val/test |
| **Результат** | Random Forest: val F1 **0.552**, test F1 **0.475** vs LR test F1 **0.443** |

### Эксп. 2 — KNN не подходит

| | |
|---|---|
| **Гипотеза** | Метод ближайших соседей уловит локальные паттерны |
| **Проверка** | KNN (k=15) + StandardScaler |
| **Результат** | test F1 **0.314** — хуже baseline, отбрасываем |

### Эксп. 3 — Подбор гиперпараметров (RandomizedSearchCV)

| | |
|---|---|
| **Гипотеза** | Настройка `n_estimators`, `max_depth` улучшит Random Forest |
| **Проверка** | RandomizedSearchCV, scoring=`f1`, 8 итераций |
| **Результат** | Лучшие params: `n_estimators=500`, `min_samples_leaf=5`; tuned val F1 ≈ baseline RF |

### Эксп. 4 — Выбор не по ROC-AUC

| | |
|---|---|
| **Гипотеза** | Модель с max ROC-AUC даст лучший практический результат |
| **Проверка** | Сравнение Gradient Boosting (max ROC-AUC) и Random Forest |
| **Результат** | GB: ROC-AUC **0.834**, но test F1 **0.356**; RF: ROC-AUC 0.830, test F1 **0.475** → берём RF |

| Модель | F1 (val) | F1 (test) | ROC-AUC (test) |
|--------|----------|-----------|----------------|

## 6. Финальная модель и интерпретируемость

**Модель:** Random Forest (`models/best_model.pkl`), обучена на train+val, выбор по **max val F1**.

**Важность признаков** (ноутбук `3_experements.ipynb`): сильнее всего влияют `delivery_delay_days` и `delivery_time_days` — долгая или опоздавшая доставка чаще совпадает с плохим отзывом. Суммы заказа влияют слабее.

**Интерпретация для продакта:** при высокой вероятности недовольства имеет смысл проактивно связаться с клиентом или ускорить доставку; порог вероятности можно поднять, если важнее precision (меньше ложных тревог).

**Ограничения:** редкий класс → F1 ~0.48; текст отзыва почти не разбираем; часть признаков известна только после доставки/отзыва.
