## Описание задачи

Нужно заранее понять, останется ли покупатель недоволен заказом. Недовольство берём из отзыва: оценка **1–2** — плохо, **3–5** — нормально.

| | |
|---|---|
| **Задача** | Классификация: доволен / недоволен |
| **Датасет** | [Olist Brazilian E-Commerce](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) |
| **Целевая переменная** | `1` — недоволен (`review_score ≤ 2`), `0` — доволен |
| **Главная метрика** | **F1-score** для класса «недоволен» |
| **Дополнительно** | Точность (precision), полнота (recall), ROC-AUC |

### Почему главная метрика — F1, а не accuracy и не только ROC-AUC

**Про дисбаланс классов.** В данных только около **13%** заказов с плохим отзывом, остальные — с хорошим. Если модель всегда отвечает «всё хорошо», accuracy будет высокой (~87%), но она бесполезна: мы не находим недовольных клиентов.

**Что такое F1 простыми словами.** F1 показывает, насколько хорошо модель находит именно **недовольных** и при этом не слишком часто ошибается. Это баланс между:
- **Точностью** — из всех, кого модель назвала «недоволен», сколько действительно недовольны;
- **Полнотой** — из всех реально недовольных, скольких модель нашла.

Для нашей задачи это важнее, чем «общая доля угаданных ответов».

**Зачем тогда ROC-AUC.** ROC-AUC показывает, умеет ли модель **ранжировать** заказы: рискованные выше, спокойные ниже. Это полезно дополнительно, но **модель для сдачи выбираем по F1 на проверочной выборке**, потому что нам важно именно находить недовольных, а не только правильно упорядочивать вероятности.

**Если метрики спорят.** Если у модели выше ROC-AUC, но ниже F1 — выбираем модель с **лучшим F1**.

### Как делим данные и почему нет утечки (data leakage)

Данные **сортируем по дате покупки** и режем по времени:
- **64%** — обучение (старые заказы),
- **16%** — проверка при обучении (validation),
- **20%** — финальный тест (самые новые заказы).

**Почему так:** модель не должна учиться на заказах из «будущего» и проверяться на прошлом — это было бы нечестно и завышало бы качество.

**Что ещё проверили:** в признаки **не** кладём саму оценку отзыва (`review_score`) — только сумму, доставку, задержку и т.п. Все суммы считаем **внутри одного заказа**, без информации из других заказов.

## Результаты

Полная таблица: `data/processed/experiments.csv` (после `make train`).

| Модель | F1 на тесте | ROC-AUC на тесте | Комментарий |
|--------|-------------|------------------|-------------|
| Логистическая регрессия | 0.443 | 0.811 | Простой baseline |
| KNN | 0.314 | 0.781 | Слабый результат |
| **Случайный лес (Random Forest)** | **0.475** | 0.830 | **Итоговая модель** |
| XGBoost | 0.472 | 0.832 | |
| LightGBM | 0.476 | 0.833 | Чуть выше ROC-AUC, но не лучший F1 на validation |
| Gradient Boosting | 0.356 | 0.834 | Самый высокий ROC-AUC, но слабый F1 |

### Почему итоговая модель — Random Forest, хотя у других выше ROC-AUC

Коротко: **нам важнее находить недовольных клиентов (F1), а не только хорошо сортировать заказы по риску (ROC-AUC).**

Подробнее:
1. **Random Forest** дал **лучший F1 на проверочной выборке** — это наш главный критерий выбора.
2. У **Gradient Boosting** и **LightGBM** ROC-AUC чуть выше (~0.83), но **F1 заметно ниже**. Значит, при обычном пороге «вероятность ≥ 0.5» они **реже помечают реально недовольных** — для редкого класса это критично.
3. ROC-AUC может быть высоким, даже если модель «осторожная» и редко ставит метку «недоволен». Для бизнеса это хуже, чем модель, которая чаще правильно ловит проблемные заказы.
4. После **подбора гиперпараметров** (RandomizedSearchCV) Random Forest **остаётся лучшим по F1**.

Итог: **сохраняем Random Forest** в `models/best_model.pkl`.
